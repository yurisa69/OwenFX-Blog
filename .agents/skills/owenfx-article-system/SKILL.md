# OwenFX 文章系统规范

## 1. 内容与数据边界

- 每篇文章的正文源文件是 GitHub 仓库 `content/articles/{slug}.md` 中独立的 Markdown 文件。
- Supabase 保存文章元数据、状态、作者/归属、修订及业务关系；文章正文与 GitHub 文件之间通过仓库现有同步逻辑关联。
- 不要将文章正文擅自迁移到 Supabase，也不要将整篇 Markdown 内容复制到其他存储作为新的权威来源。
- 先检查 `lib/github-articles.ts`、`lib/article-records.ts`、文章 API 路由和同步任务实现，再确定读写流程。
- 保留现有文章、草稿、修订、回收站/归档状态、同步任务与恢复能力；不得擅自批量改写或删除历史文章。

## 2. 标题层级与编号

以 `docs/ARTICLE-WRITING-GUIDELINES.md` 为准。当前规则：
- 文章可设置至多一个不编号的 H1 主标题，必须位于正文步骤之前；主标题不参与步骤编号。若没有独立主标题，第一个编号 H1 可直接作为正文步骤。后续正文一级步骤标题使用 H1 和中文数字加顿号：`# 一、环境准备`。
- 前言、引言、概述、目录、总结、结语、官方资料、参考资料、参考文献、延伸阅读、附录、致谢、相关链接等结构性章节不参与正文步骤编号，按文档实际结构保留合适标题层级；不得将结构性章节误计为正文步骤或重置步骤编号。
- 二级标题使用 H2，阿拉伯数字加英文半角句点：`## 1. 安装 Docker`；每个 H1 步骤下重新从 1 开始。结构性章节不应被强行纳入步骤编号。
- 三级标题使用 H3，直接使用 Unicode 带圈数字：`### ① 检查系统`；每个 H2 下从 ① 开始。
- 四级及以下优先使用列表。
- 不用 `1.1`、`1.1.1` 替代标题层级，不通过 CSS/脚本伪造标题编号。
- 不擅自批量改写历史文章；只有用户明确要求修改的文章才按当前规范调整。
- 发布前使用现有编号校验逻辑；自动修正无法安全判断的内容应提示人工处理，不可静默重写。

## 3. 编辑器与内容往返

- 保留 Markdown 模式、富文本模式、预览、草稿、手动发布、修订历史和恢复能力。
- Markdown → HTML → Markdown 往返时，尽量保持语义与内容：标题、段落、换行、粗斜体、列表、引用、表格、链接、图片、代码块和语言标识。
- 修改编辑器状态同步时，注意避免每次键入都重写 `innerHTML` 导致光标跳动、选区丢失或输入法异常。
- 切换编辑模式前先将当前模式内容安全同步；不要丢弃未保存输入。
- 对富文本 HTML 进行解析和过滤，不得直接信任用户粘贴内容。
- 代码块语言信息必须在 Markdown、富文本转换、保存、预览和正文渲染链路中保持一致。
- 表格、脚注、任务列表、图片尺寸等兼容行为以现有测试和实现为基准，不随意替换 Markdown 解析器。

## 4. Markdown 渲染与代码块

当前渲染链路位于 `lib/markdown.ts`，使用 remark、remark-gfm、remark-rehype、rehype-sanitize、Shiki（通过 `@shikijs/rehype`，采用 Dracula 主题）和 rehype-stringify。修改前先阅读当前插件顺序、sanitize schema 与兼容处理。

- 保留代码块语言标识与语法高亮；不能仅凭语言名称判断是否高亮成功，应检查最终 HTML class 和样式规则。
- 代码块的复制按钮、语言标签、滚动、换行和移动端显示属于既有交互，除非用户明确要求，不得顺手更改。
- Bash/Shell、JSON、YAML、JavaScript/TypeScript、HTML、CSS、SQL 等语言应按真实语言标识处理；未知或缺失语言应有安全回退。
- 不把所有代码块统一当成 Bash，也不要为追求颜色而错误识别纯文本。
- sanitize 必须继续限制危险标签、属性、URL 和不可信 HTML；不能为修复高亮而放开任意 HTML。

## 5. 图片、视频与 R2

- 图片、GIF、WebP、AVIF、头像、背景图、软件图标、视频等媒体二进制由 Cloudflare R2 存储。
- Supabase `media_assets` 保存媒体元数据、归属和关联，不存储二进制文件。
- 文章编辑器按当前流程请求短时签名 URL，浏览器直传 R2，再由服务端验证对象并登记元数据。
- 不把 R2 Secret、签名密钥或服务端凭据暴露给浏览器。
- 不因编辑器删除图片引用就自动删除 R2 对象；删除前必须确认没有其他文章、评论、软件或用户资料引用，并遵守授权要求。
- 保持现有图片替代文本、懒加载、尺寸、引用和视频链接兼容行为。

## 6. 草稿、发布、版本与同步

- 草稿与正式发布状态必须清晰区分；预览不等于发布。
- 发布前检查标题、Slug、正文、编号、链接、媒体引用和权限。
- 版本恢复应创建/记录新的修订状态，不直接抹除历史记录。
- GitHub 同步是异步或可失败流程时，明确区分排队、处理中、成功、失败、冲突和可重试状态。
- 保持现有幂等键、任务租约、文章锁和失败释放逻辑；不要绕过同步锁直接覆盖文章文件。
- 对冲突必须读取当前远端版本并比较，不可盲目覆盖他人或更新中的内容。
- 用户明确要求手动发布；不得把保存草稿、同步成功或构建成功误认为已经发布文章。

## 7. 测试与回归

优先检查并运行仓库现有测试：
- `npm run test:markdown`
- `npm run test:editor`
- `npm test`
- `npm run lint`
- `npm run build`

涉及编号时检查 `tests/article-numbering.test.mjs`；涉及转换时检查 `tests/article-editor-conversion.test.mjs`；涉及 Markdown 渲染时检查 `tests/markdown-compat.test.mjs`。以当前 `package.json` 为准，不假定脚本永远不变。

至少覆盖：Markdown/富文本往返、代码语言保留、危险 HTML 过滤、标题编号、预览、草稿保存、发布、版本恢复、同步失败/重试和移动端阅读。

## 8. 修改纪律

先定位相关组件、API、数据库引用和测试；先列出本次修改范围。文章内容变更与编辑器代码变更分开评估。不得为了修复文章显示而修改无关文章、删除历史版本、变更数据库结构或调整软件详情页。
