# OwenFX 性能规范

## 1. 原则

以真实用户体验和可测量数据为依据，先定位瓶颈，再做最小优化。不得为了追求单一 Lighthouse 分数而破坏功能、视觉设计、可访问性、搜索引擎可见性或数据一致性。

默认保护现有架构与设计，不引入不必要的依赖，不做未经要求的全站重构。

## 2. Next.js 与渲染

- 先确认组件是 Server Component 还是 Client Component；仅在确实需要状态、事件或浏览器能力时使用客户端组件。
- 保留 App Router 当前数据读取方式、Supabase SSR 身份上下文和服务端权限边界。
- 检查重复请求、过度获取字段、无界列表、瀑布请求和不必要的客户端状态。
- 对动态内容、用户态、缓存和 revalidation 逐项确认语义；不能为了缓存而缓存个性化或权限敏感数据。
- 不将服务端密钥、管理数据或用户隐私放进客户端组件。
- 避免不必要的全局事件监听、重复订阅、频繁状态更新和昂贵的 render 计算。

## 3. 图片与媒体

- 优先为图片提供明确尺寸或宽高比，避免加载后布局跳动（CLS）。
- 视实际场景使用懒加载、异步解码、合适尺寸和响应式资源；首屏关键图片不应被错误地延迟。
- 保留 R2 当前媒体路径、公开 URL、元数据和授权机制；性能优化不能绕过签名上传或媒体归属校验。
- 视频不应默认自动下载完整文件；按需加载并保留浏览器 Range 播放能力。
- 不因缓存优化而覆盖对象、删除旧媒体或改变长期引用 URL。
- 对第三方图标/图片检查来源、失败回退和尺寸稳定性。

## 4. 动画与视觉稳定性

- 对循环动画、模糊、阴影、滤镜、粒子、渐变和 transform 检查重绘/合成成本；避免大量元素持续触发布局或绘制。
- 优先使用合适的 transform/opacity 动画；不要把所有动画都改成 GPU 强制提升。
- 保留用户已确认的动效参数。未被明确要求时，不改动画时长、色相、透明度、运动范围或触发条件。
- 防止首次加载闪烁、主题切换闪白、内容加载后卡片尺寸变化、滚动条出现/消失导致横向跳动。
- 对移动端检查低刷新率、弱设备、触控滚动和页面后台切换后的动画行为。

## 5. 减少动态效果与可访问性

- 必须尊重系统媒体查询 `prefers-reduced-motion: reduce`。
- 在减少动态效果模式下，关闭或显著降低非必要的循环粒子、视差、自动滚动、缩放/位移动画和持续呼吸效果。
- 保留必要的状态变化、加载进度、焦点提示和操作反馈；不能让用户因关闭动画而无法理解交互结果。
- 不以 JavaScript 反复读取媒体查询并频繁更新状态；优先使用 CSS 媒体查询，确有必要时集中处理并清理监听。
- 检查系统偏好变化是否即时生效，以及主题、导航和编辑器是否出现闪烁或状态错乱。

## 6. 加载与数据流

- 仅在确实改善首屏体验且不改变语义时使用流式加载、分页或延迟加载。
- 保留加载、空数据、错误和重试状态；不要因 skeleton 或占位内容造成明显布局跳动。
- 对长列表采用有界查询、分页或现有虚拟化方案；先核对排序、筛选、收藏和分页行为。
- 避免多个组件重复请求相同数据；共享请求时注意用户身份和缓存隔离。
- 不把实时更新、统计事件或后台同步静默改成可能丢数据的异步 fire-and-forget。

## 7. 测量与回归

先确定基准和目标设备，再进行优化。按任务适用范围检查：
- Next.js build 与 bundle/路由输出。
- 浏览器 Network、Performance、Console 与布局偏移。
- 图片/视频请求体积、加载优先级、缓存头和失败回退。
- 首屏可见内容、交互响应、长任务和动画帧稳定性。
- 手机、平板、桌面，深色/浅色，以及减少动态效果模式。

如果没有真实性能数据，明确标注为代码层面的风险判断，不编造毫秒数、FPS、Core Web Vitals 或性能提升百分比。

## 8. 修改流程

1. 复现或测量问题，确定瓶颈位于网络、服务端、客户端脚本、布局还是动画。
2. 检查目标组件及共享依赖，确认副作用和数据边界。
3. 列出本次修改范围，只处理已定位问题。
4. 修改后运行适用测试、lint、build，并对比同一场景。
5. 检查视觉一致性、交互、可访问性和移动端回归。
6. 报告基准、改动、验证证据和未测范围。

不得仅为减少动画而删除用户明确保留的动效；不得以性能为由改变页面内容、导航结构或业务功能。
