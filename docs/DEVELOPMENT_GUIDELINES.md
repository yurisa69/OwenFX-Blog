# OwenFX 开发与 Git 操作规范

本文适用于本仓库的所有开发者、AI 编程工具和自动化工作流。修改代码前应先阅读本文，并遵守仓库现有架构、安全要求和用户已确认的项目决定。

## 1. 统一语言规范

1. 所有面向用户、开发者和项目协作者展示的 Git 操作说明，默认使用简体中文。
2. Commit 提交说明必须使用简体中文，准确概括本次修改，不使用英文前缀作为主要说明。
3. 普通开发分支名称优先使用简体中文；固定正式分支 `main` 保留原名，不翻译、不重命名。
4. Pull Request（合并请求）的标题、正文、审查意见和合并说明使用简体中文。
5. 版本发布说明、变更记录、回退说明、检查结果和部署报告使用简体中文。
6. 不要在同一条提交说明或操作报告中无必要地中英混排；确有必要的技术名词可保留英文原文，并在首次出现时用中文解释。
7. GitHub 网站自身的按钮、菜单、系统状态等界面语言由 GitHub 账户或产品界面设置决定，仓库文件不能强制改变 GitHub 原生界面的显示语言。

## 2. 提交说明规范

提交说明必须使用简体中文，简洁、明确、可追溯。优先采用以下格式：

- `修复：文章代码块语法高亮异常`
- `优化：首页轮动卡牌动画`
- `新增：软件详情页信息展示`
- `调整：移动端底部导航图标`
- `升级：项目依赖版本`
- `文档：补充本地部署说明`
- `回退：恢复至指定稳定版本`

要求：

1. 一次提交说明对应一组完整、相关且已检查的修改。
2. 不使用“更新”“修改了一些内容”“修复问题”等无法说明实际内容的模糊描述。
3. 不得为了让提交记录看起来整齐而拆成逐文件提交或无必要的多个提交。
4. 不得把未实际完成的修改写成已完成。

## 3. 分支命名规范

1. 正式分支固定为 `main`，作为生产源码分支；不得擅自重命名。
2. 确实需要隔离开发时，普通开发分支优先使用中文名称，可采用以下形式：
   - `功能/文章编辑器`
   - `修复/代码高亮`
   - `优化/首页动画`
   - `升级/项目依赖`
3. 分支名称应简短、明确，不包含空格、控制字符或无意义编号。
4. Git 固定引用和平台要求的名称（例如 `main`、`origin`、`HEAD`）保留原样。
5. 创建分支前先检查是否已有同名分支；不得擅自创建分支、Pull Request 或预览部署。是否需要独立分支，应依据用户明确要求和任务风险决定。
6. 中文分支名称属于仓库命名约定；若某个外部工具、脚本或部署集成不兼容，先说明具体限制，再选择兼容方案，不得静默改成英文。

在聊天、提交报告、项目文档和协作说明中统一使用以下中文名称：

## 5. OwenFX 提交与推送流程

1. 操作前检查仓库、当前分支、工作区状态、远程分支状态和相关源码。
2. 修改前明确列出本次计划修改的文件或范围；保护现有设计、功能、业务逻辑和用户数据。
3. 完成全部相关修改后统一检查，不逐文件提交，不分批提交或推送。
4. 检查通过后，原则上一次性创建一个中文提交说明的完整提交，并按用户确认的目标分支一次性推送。
5. 用户已指定直接更新 `main` 时，不擅自创建分支、合并请求或预览部署；若存在冲突、保护规则或其他阻断，先停止并如实说明。
6. 不使用强制推送覆盖远程历史；不得擅自重写、删除或覆盖他人提交。
7. 推送成功后，单独核对 GitHub 目标分支的最新提交，不把本地提交成功误报为远程推送成功。
8. 仅在 Vercel 确认收到对应提交后，继续核对构建与生产部署状态。

## 6. 检查与部署报告

所有执行报告使用简体中文，并分别说明实际结果。建议格式：

1. 源码检查：通过 / 未通过 / 未执行
2. 修改内容：列出实际修改的文件和内容
3. 提交：成功 / 失败 / 未执行，并提供提交说明和 Commit SHA
4. 推送：成功 / 失败 / 未执行，并注明目标分支
5. GitHub 检查：通过 / 失败 / 进行中 / 未检查
6. Vercel 构建：成功 / 失败 / 进行中 / 未触发 / 未检查
7. 生产部署：成功 / 失败 / 进行中 / 未部署 / 未检查
8. 网站运行验证：说明实际检查的页面和功能；未验证时明确写明“未验证”

不得把提交成功、推送成功、构建成功和网站运行正常混为同一个结果。未执行的操作必须明确标注“未执行”，不得声称完成。

## 7. 安全与项目保护

1. 不提交真实密钥、Token、私钥、数据库连接凭据或未经脱敏的用户数据。
2. 不擅自删除数据库表、用户数据、有效接口、历史迁移或现有业务功能。
3. 数据库结构和数据变更必须遵守仓库现有数据库变更规范，并在执行破坏性或不可逆操作前取得明确授权。
4. 不因构建失败而擅自删除功能、降低安全策略或改变已确认的技术架构。
5. 不擅自扩大修改范围；优先采用小范围、可验证、可回退的渐进式修改。
6. Git 历史回退不等于数据库、对象存储或外部服务数据回退；必须分别评估影响。

## 8. 规范优先级

本文件补充 OwenFX 的开发协作规则，不替代 README、数据库变更规范、备份恢复手册、环境变量安全要求和用户明确确认的项目决定。出现冲突时，优先遵守安全要求和用户最新明确决定，并在执行前说明冲突。

## 9. 指定版本回退规范：main 历史回溯

### 9.1 名称与适用场景

当用户明确要求将 OwenFX 网站源码恢复到某个指定 Commit、Tag 或历史版本时，统一采用 **「main 历史回溯」**（下称“历史回溯”）。

历史回溯是一种以目标版本完整 Git Tree 为准、在当前 `main` 历史上创建新回退提交的源码恢复方式。它不是 Git 分支名称，也不是 GitHub 的强制回滚按钮。

### 9.2 核心原则

1. **目标版本的全部文件为准。** 目标 Commit 的完整 Git Tree 是恢复后的唯一文件状态基准，不以当前版本逐文件反向修改的结果作为基准。
2. **创建新的回退提交。** 新回退 Commit 必须以执行时最新的远程 `main` HEAD 作为父提交，并指向与目标版本完全一致的 Git Tree。
3. **保留历史。** 目标版本之后的旧 Commit 仍保留在 Git 历史中；不得删除、改写或隐藏这些旧提交。
4. **普通更新 main。** 新回退 Commit 是当前 `main` 的后代，只允许普通 fast-forward 更新；禁止 force push、force-with-lease、重置远程引用或其他历史重写方式。
5. **完整而非局部。** 必须恢复目标 Tree 中的所有文件和目录状态，包括文件内容、路径、文件新增与删除、重命名结果、可执行位、符号链接等 Git Tree 元数据；不得只撤销某几个功能或提交。
6. **不擅自改变目标。** 除创建回退提交所需的 Commit 元数据外，不在恢复过程中夹带新功能、修复、格式化或其他额外源码修改。

### 9.3 标准执行步骤

1. **确认目标版本。** 获取用户指定的完整 Commit SHA 或明确 Tag；核实其属于当前仓库、对象可读取且 Tree 完整。短 SHA 必须解析为唯一完整 SHA，不得猜测。
2. **核对当前 main。** 读取最新远程 `main` HEAD 和对应 Tree SHA，记录执行基准；确认工作区/远程没有未审查的并发变更。
3. **检查目标 Tree 完整性。** 获取目标 Commit 对应的完整 Tree；若 API 返回截断、分页不完整、子模块/符号链接无法可靠保留或对象缺失，停止执行，不得用不完整文件列表构造恢复版本。
4. **评估外部状态兼容性。** 对比目标版本与当前版本涉及的数据库访问、Supabase migration、RLS、R2 对象路径、外部 API、环境变量及持久化数据变化。Git Tree 只恢复仓库文件，不会自动回退数据库、用户数据、R2 对象、外部服务状态、环境变量或 Vercel 项目设置。发现潜在破坏性影响时，先说明并取得必要授权。
5. **构造目标 Tree。** 以当前 `main` Tree 为基础，创建一个内容与目标版本完整 Tree 一致的新 Tree。创建后核验新 Tree SHA 与目标 Tree SHA 完全一致；若不一致，停止，不创建或更新分支。
6. **创建回退 Commit。** 使用新 Tree 创建一个新的 Commit，父提交必须是步骤 2 记录的当前远程 `main` HEAD。提交说明使用简体中文，明确标记“回退”及目标版本。
7. **普通更新 main。** 更新前再次读取远程 `main`；只有它仍等于步骤 2 记录的 HEAD 时，才以非强制方式将 `main` 更新到新回退 Commit。不得设置 force，不得绕过分支保护。如果 HEAD 已变化、更新不是 fast-forward、权限或保护规则阻止更新，立即停止并报告。
8. **核验结果。** 更新后重新读取远程 `main`，确认 HEAD 是新回退 Commit；核对新 Commit 的父提交为原当前 HEAD，且新 Commit Tree SHA 与目标 Tree SHA 完全相同。检查差异应只反映“当前源码到目标源码”的恢复结果。
9. **统一验证与发布。** 按适用范围执行 lint、类型检查、测试和 build；随后核对 GitHub Actions 与 Vercel 自动生产部署。不得额外创建 Preview Deployment 或重复触发部署。
10. **报告事实。** 报告目标版本 SHA、回退 Commit SHA、原 main HEAD、新 Tree SHA、远程更新结果、旧历史保留情况、外部数据影响评估、测试和部署状态。未完成的检查明确标注未执行或进行中。

### 9.4 明确禁止的替代方式

- 不使用 `git reset --hard <target>` 后强制推送覆盖 `main`。
- 不使用 `git push --force` 或 `git push --force-with-lease`。
- 不通过 rebase、改写父提交、删除旧 Commit 或重建历史来伪装“无痕回退”。
- 不逐文件执行反向修改、分批提交或多个回退 Commit。
- 不把普通 `git revert` 一个或多个提交视为完整历史回溯；只有目标 Tree 完整一致才满足本规范。
- 不因目标版本较旧而擅自回退 Supabase 数据库、删除 migration、清理 R2 对象或修改外部服务。
- 不因回退后的构建失败而擅自修改目标源码；先报告失败原因，由用户决定后续修复或其他处理。

### 9.5 结果定义与边界

“源码已恢复到目标版本”必须同时满足：

- 新回退 Commit 的 Tree SHA 与目标 Commit 的 Tree SHA 完全一致；
- 远程 `main` 已指向该新回退 Commit；
- 新回退 Commit 的父提交是回退前的远程 `main` HEAD；
- 目标版本之后的旧 Commit 仍在 Git 历史中，没有被重写或删除。

因此，**源码文件状态与目标版本完全一致，但 Git 历史不会与目标版本相同**。这是“main 历史回溯”的预期结果。

历史回溯只影响 Git 仓库中的源码文件状态。数据库记录、用户数据、Supabase migration 执行历史、R2 文件、环境变量、Vercel 项目配置和其他外部服务状态均独立存在；任何需要改变这些内容的操作都必须单独评估、单独授权并单独执行。
