# OwenFX 开发与 Git 操作规范

本文适用于本仓库的所有开发者、AI 编程工具和自动化工作流。修改代码前应先阅读本文，并遵守仓库现有架构、安全要求和用户已确认的项目决定。

## 1. 统一语言规范

1. 所有面向用户、开发者和项目协作者展示的 Git 操作说明，默认使用简体中文。
2. Commit 提交说明必须使用简体中文，准确概括本次修改，不使用英文前缀作为主要说明。
3. 普通开发分支名称优先使用简体中文；固定正式分支 `main` 保留原名，不翻译、不重命名。
4. Pull Request（合并请求）的标题、正文、审查意见和合并说明使用简体中文。
5. 版本发布说明、变更记录、回退说明、检查结果和部署报告使用简体中文。
6. 不要在同一条提交说明或操作报告中无必要地中英混排；确有必要的技术名词可保留英文原文，并在首次出现时用中文解释。
7. GitHub 网站自身的按钮、菜单、系统状态等界面语言由 GitHub 账户或产品界面设置决定，仓库文件不能强制改变 GitHub 原生界面的显示语言。

## 2. 提交说明规范

提交说明必须使用简体中文，简洁、明确、可追溯。优先采用以下格式：

- `修复：文章代码块语法高亮异常`
- `优化：首页轮动卡牌动画`
- `新增：软件详情页信息展示`
- `调整：移动端底部导航图标`
- `升级：项目依赖版本`
- `文档：补充本地部署说明`
- `回退：恢复至指定稳定版本`

要求：

1. 一次提交说明对应一组完整、相关且已检查的修改。
2. 不使用“更新”“修改了一些内容”“修复问题”等无法说明实际内容的模糊描述。
3. 不得为了让提交记录看起来整齐而拆成逐文件提交或无必要的多个提交。
4. 不得把未实际完成的修改写成已完成。

## 3. 分支命名规范

1. 正式分支固定为 `main`，作为生产源码分支；不得擅自重命名。
2. 确实需要隔离开发时，普通开发分支优先使用中文名称，可采用以下形式：
   - `功能/文章编辑器`
   - `修复/代码高亮`
   - `优化/首页动画`
   - `升级/项目依赖`
3. 分支名称应简短、明确，不包含空格、控制字符或无意义编号。
4. Git 固定引用和平台要求的名称（例如 `main`、`origin`、`HEAD`）保留原样。
5. 创建分支前先检查是否已有同名分支；不得擅自创建分支、Pull Request 或预览部署。是否需要独立分支，应依据用户明确要求和任务风险决定。
6. 中文分支名称属于仓库命名约定；若某个外部工具、脚本或部署集成不兼容，先说明具体限制，再选择兼容方案，不得静默改成英文。

## 4. Git 操作说明用语

在聊天、提交报告、项目文档和协作说明中统一使用以下中文名称：

| Git / 平台术语 | 统一中文用语 |
| --- | --- |
| Commit | 提交 / 提交记录 |
| Commit Message | 提交说明 |
| Push | 推送 |
| Pull | 拉取 |
| Fetch | 获取远程更新 |
| Branch | 分支 |
| Merge | 合并 |
| Pull Request | 合并请求 |
| Tag | 版本标签 |
| Checkout / Switch | 切换分支 |
| Revert | 反向撤销提交 |
| Reset | 重置 |
| Rollback | 回退 |
| Restore | 恢复 |
| Working Tree | 工作区 |
| Staging Area | 暂存区 |
| Remote Repository | 远程仓库 |
| Local Repository | 本地仓库 |
| Conflict | 合并冲突 |

命令、参数、分支固定名称、Commit SHA、文件名、目录名、API 字段和配置键必须保留准确原文。例如：`git commit`、`git push origin main`、`package.json`、`main`、`a1b2c3d`。中文化说明不等于翻译或修改可执行命令。

## 5. OwenFX 提交与推送流程

1. 操作前检查仓库、当前分支、工作区状态、远程分支状态和相关源码。
2. 修改前明确列出本次计划修改的文件或范围；保护现有设计、功能、业务逻辑和用户数据。
3. 完成全部相关修改后统一检查，不逐文件提交，不分批提交或推送。
4. 检查通过后，原则上一次性创建一个中文提交说明的完整提交，并按用户确认的目标分支一次性推送。
5. 用户已指定直接更新 `main` 时，不擅自创建分支、合并请求或预览部署；若存在冲突、保护规则或其他阻断，先停止并如实说明。
6. 不使用强制推送覆盖远程历史；不得擅自重写、删除或覆盖他人提交。
7. 推送成功后，单独核对 GitHub 目标分支的最新提交，不把本地提交成功误报为远程推送成功。
8. 仅在 Vercel 确认收到对应提交后，继续核对构建与生产部署状态。

## 6. 检查与部署报告

所有执行报告使用简体中文，并分别说明实际结果。建议格式：

1. 源码检查：通过 / 未通过 / 未执行
2. 修改内容：列出实际修改的文件和内容
3. 提交：成功 / 失败 / 未执行，并提供提交说明和 Commit SHA
4. 推送：成功 / 失败 / 未执行，并注明目标分支
5. GitHub 检查：通过 / 失败 / 进行中 / 未检查
6. Vercel 构建：成功 / 失败 / 进行中 / 未触发 / 未检查
7. 生产部署：成功 / 失败 / 进行中 / 未部署 / 未检查
8. 网站运行验证：说明实际检查的页面和功能；未验证时明确写明“未验证”

不得把提交成功、推送成功、构建成功和网站运行正常混为同一个结果。未执行的操作必须明确标注“未执行”，不得声称完成。

## 7. 安全与项目保护

1. 不提交真实密钥、Token、私钥、数据库连接凭据或未经脱敏的用户数据。
2. 不擅自删除数据库表、用户数据、有效接口、历史迁移或现有业务功能。
3. 数据库结构和数据变更必须遵守仓库现有数据库变更规范，并在执行破坏性或不可逆操作前取得明确授权。
4. 不因构建失败而擅自删除功能、降低安全策略或改变已确认的技术架构。
5. 不擅自扩大修改范围；优先采用小范围、可验证、可回退的渐进式修改。
6. Git 历史回退不等于数据库、对象存储或外部服务数据回退；必须分别评估影响。

## 8. 规范优先级

本文件补充 OwenFX 的开发协作规则，不替代 README、数据库变更规范、备份恢复手册、环境变量安全要求和用户明确确认的项目决定。出现冲突时，优先遵守安全要求和用户最新明确决定，并在执行前说明冲突。


## 9. Vercel 工具与临时环境生命周期

1. Vercel Sandbox 仅用于需要隔离环境的源码检查、依赖安装、测试、类型检查、构建和 AI 修改验证；普通只读文档查询不必创建 Sandbox。
2. 每次任务从 GitHub 最新 main 的明确 Commit SHA 创建全新 Sandbox，使用非持久化配置（persistent: false），不得从旧快照恢复，不得挂载已有 Drive，不得创建快照。
3. Sandbox 内只使用测试所需的虚构/占位环境变量；不得拉取或复制生产 .env、密钥、Token、Supabase 生产数据或 Cloudflare R2 对象。
4. Sandbox 不作为正式修改来源。最终变更必须经过完整差异审查，并按本文件既定流程统一提交和推送。
5. 每次 Sandbox 任务结束后，无论成功、失败或中止，都必须先记录必要的非敏感检查结论，再停止会话、删除本次 Sandbox，并核验本次创建的 Sandbox/快照/Drive 等资源均已清理。不得保留工作目录、依赖目录、构建产物、日志副本、快照或其他临时内容。
6. 不得为了清理本次环境而删除其他任务或用户已有的 Sandbox、Snapshot、Drive；如果本次操作误建了持久化资源，先确认其归属和内容，再清理本次资源。
7. Vercel Web Analytics 与 Speed Insights 通过官方 Next.js 组件接入根布局；还需在 Vercel 项目控制台分别启用。未完成控制台启用前，不得声称数据采集已生效。
8. Web Analytics 用于聚合访问量、页面浏览、热门页面、来源、设备/浏览器等分析；Speed Insights 用于真实用户 Core Web Vitals 和性能趋势。数据不足时标注样本不足，不编造趋势或指标。
9. Analytics 不得采集或发送用户 ID、邮箱、认证信息、Token、私密文章内容、表单内容或其他敏感信息；不得将用户级分析数据或导出文件提交到 Git。
10. Vercel Toolbar 用于按需诊断布局偏移、交互耗时和无障碍问题。不得为使用 Toolbar 擅自创建 Preview Deployment；生产环境可见性设置只有在用户授权时才临时调整，检查后恢复原设置。
11. Vercel 工具使用规范的详细步骤以 .agents/skills/owenfx-vercel-tooling/SKILL.md 为准。
